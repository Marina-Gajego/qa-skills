# Validation — proving the new test is sound

Use the commands the repo documents (`stack.md` → How to run, `package.json` scripts, README, CI) before the generic ones below. Generic commands are the tool's standard CLI; say so when you use one.

## 1. Static checks (always — no environment needed)

| Stack | Compile / type-check | List / dry-run (finds undefined steps, bad imports, duplicate titles) |
|---|---|---|
| Playwright (TS/JS) | `npx tsc --noEmit` when the repo has TypeScript and a `tsconfig.json`; otherwise see "TypeScript without tsc in the repo" below | `npx playwright test --list <new spec or -g "<title>">` |
| Cypress | `npx tsc --noEmit` if TS | none built in — rely on tsc/lint |
| Cucumber JVM + Maven | `mvn -q test-compile` | `mvn test -Dcucumber.features=<feature> -Dcucumber.execution.dry-run=true` (JUnit Platform engine) — needs no app, but the runner may filter tags; check the runner class |
| Cucumber JVM + Gradle | `./gradlew compileTestJava` | dry-run via the runner property, as above |
| cucumber-js / playwright-bdd | `npx tsc --noEmit` | `npx cucumber-js --dry-run <feature>` · `npx bddgen` then `npx playwright test --list` |
| pytest / pytest-bdd | `python -m py_compile <files>` | `pytest --collect-only -q <path>` |
| behave | — | `behave --dry-run <feature>` |
| Robot Framework | — | `robot --dryrun <suite>` |
| .NET (SpecFlow/Reqnroll, NUnit, xUnit) | `dotnet build` | `dotnet test --list-tests` |
| Go | `go vet ./...` | `go test -run XXX_NONE ./...` (compiles tests, runs none) |

Plus:
- `python3 -I <skill>/scripts/reuse_index.py <repo> --check <each new/changed .feature>` — must show no `UNDEFINED` and no `AMBIGUOUS`.
- The linter/formatter the repo configures (`eslint`, `prettier --check`, `checkstyle`, `ruff`…) on the files you touched — only if it's already set up; never add one.
- If you changed existing code: the list/compile step for the whole suite, so you know existing tests still load.

**TypeScript without tsc in the repo.** Playwright runs `.ts` without TypeScript installed, so many repos have no `typescript` dependency — and `--list` doesn't catch type errors (a wrong argument type, a misspelled locator field). Type-check anyway, without touching the repo, from the npx cache:

```bash
npx -y -p typescript@5 tsc --noEmit --strict --skipLibCheck --target es2022 --module esnext \
  --moduleResolution bundler --types node <new and changed .ts files>
```

Files named on the command line make tsc ignore any `tsconfig.json`, and imports still resolve through the repo's `node_modules`. Report errors in the files you wrote and fix them; errors that already existed in untouched files are noted, not fixed. If `--strict` flags patterns the existing code uses everywhere, re-run without it and say so. Drop `--types node` if the repo has no `@types/node`. Never add `typescript` or a `tsconfig.json` to the repo.

**Java version.** Use the JDK the project declares (`maven.compiler.release`, toolchain files, CI). If the default `java` is newer and the build breaks (Lombok and annotation processors often do), look for an installed matching JDK (`/usr/libexec/java_home -V` on macOS, `~/.sdkman`, `~/Library/Java/JavaVirtualMachines`) and run with `JAVA_HOME` set for that command only.

Dependencies missing (no `node_modules`, Maven offline without cache)? Don't install them — say the static check couldn't run and why, and give the command.

## 2. Running the new tests (only when safe and possible)
All of these must hold:
- the environment is local, or one the `.qa-skills/` files or the user mark as allowed for automated tests (never production, never a shared environment where the test writes data unless allowed);
- the app/API answers (a quick request to the base URL or health endpoint);
- what the test needs is available without asking for secrets (env vars already set, `.env` present, storage state generated by the suite's own setup);
- the first run targets **only the new tests**: by file, `-g "<title>"`, `--grep`, `-Dcucumber.features=<file>`, `-k`, etc. A setup project the runner pulls in by dependency (auth setup) is fine. The wider run below comes after, and only against a local or explicitly allowed test environment.

**Make sure the filter filtered.** Read the runner's summary: the number of tests run should be the new ones (plus a setup project it depends on). Cucumber JVM runner classes often pin `FILTER_TAGS_PROPERTY_NAME`/`@IncludeTags`, and then `-Dcucumber.filter.tags` is ignored and the whole suite runs — use `-Dcucumber.features=<feature file>[:<line>]` instead. If the filter didn't work, say which command does.

**Then run with the neighbors.** When the new tests touch shared state (login/logout, the shared test user, seeded records, global settings) or you changed existing code, run once more with the tests that share it — usually the whole local suite in its normal parallel mode. A test that passes alone and breaks others in parallel is the most expensive kind of new test.

A **local** app that's down may be started once, in the background, if the repo (or the product repo) documents a start command that needs no credentials and changes nothing shared (`npx <server>`, `docker run …`, `yarn start`). Never run setup wizards, migrations or seeds that reset data other people use. Stop what you started when you're done.

Not all true → don't run; report "not executed", the reason, and the exact command.

## 3. Reading a failure

| Cause | What you do |
|---|---|
| Your code (wrong selector, step not wired, typo, missing await, wrong data) | Fix it and re-run. Selectors: confirm against the product code or a live snapshot. |
| The product does something other than the oracle says | Keep the assertion. Mark the test the way the team marks known defects, report it as a probable defect with evidence (expected vs actual, source of the expectation). |
| Environment (app down, DB unreachable, auth setup failing for everyone) | Report it; don't change the test to work around it. |
| Flaky timing | Use the suite's own wait strategy (web-first assertions, existing wait helpers). Never add hard sleeps unless the team does and says why. |

Never make a test pass by loosening an assertion, adding a retry, catching an error or skipping it silently.
